| `tools/prepare_publish.py` | ソースからフラットな公開用フォルダを作る任意の開発補助 |
| `publish/` | iPhoneのファイル選択だけで配置できる公開用19ファイル |
| `GUIDE.md` | iPhoneからの公開、iPhone・Android利用、バックアップ手順 |
| `TEST-RESULTS.md` | 実施済み・未検証・仕様上の扱い |

通常の修正はルートのソースを変更し、公開用ファイルも更新します。`publish/` は同じコードで、`./assets/` 参照だけを `./` にしたものです。利用者が変換スクリプトを実行する必要はありません。

## データモデル

IndexedDBデータベース名は`umalog`、DBバージョンは1です。`state`ストアの`main`キーに、以下の分離された配列を含むスナップショットを保存します。レース・馬券・買い目はIDで関連付け、単一トランザクションでまとめて更新します。

| データ | 主なフィールド |
| --- | --- |
| バックアップ全体 | `schemaVersion:1`, `races`, `tickets`, `lines`, `reviews`, `settings`, `character`, `growth` |
| races | `id`, `date`（開催日）, `venue`, `number`, `name` |
| tickets | `id`, `raceId`, `type`, `kind`（reported/advance）, `memo`, `createdAt`（端末時刻） |
| lines | `id`, `ticketId`, `numbers`, `stake`, `status`, `payout`, `refund` |
| reviews | `id`, `week`（月曜日の日付）, `text` |
| settings | `name`, `motion` |
| character | `exp`, `level`, `stage`（再計算可能な派生値） |
| growth | 週ごとのA〜EのEXPと集計値（再計算可能な育成履歴） |

すべての一次記録には暗号学的乱数から作るIDを付与。設定・キャラクターは一人につき一つの単一オブジェクトです。週別育成履歴は月曜日の日付を自然キーとします。

将来の衣装・背景はsettingsに識別子を追加し、表示層で素材を重ねる構造にできます。進化閾値はcore.jsのSTAGES、名称はSTAGE_NAMES、素材はstage-N.svgで分離済みです。フォーメーションはcore.jsに組み合わせ生成関数を追加し、既存のlinesモデルへ渡せます。

## 集計の詳細

- 金額は安全な整数のみ。1行の金額上限は1兆円、全行合計もJavaScriptの安全整数範囲内を検証します。購入は正の100円単位、払戻・返還は1円単位。
- 未確定行は確定購入・収支・回収率・買い目的中率から除外。未確定購入額は別表示します。
- 全額返還の確定行は返還額を収支・回収率に含め、買い目・レース的中率の有効分母から除外します。
- 一部返還は有効買い目として扱います。返還が購入額を上回る入力、全額返還＋払戻はエラーにします。
- レース的中率は、そのレースの全券種・全行確定後のみ集計します。全額返還のみのレースは除外します。
- 買い目別の別行追加購入は別の買い目行として数えます。合算を選ぶと1行です。
- 枠連BOXは選んだ異なる枠同士を生成。枠連ゾロ目は通常入力で追加できます。
- 同一レースの名称は共通です。記録編集で開催日・場・番号を変えると、編集した券種の記録だけを対応レースへ移動します。
- 開催日から日本時間の週を決定します。Aはその週の最初の「全行確定レース」で10EXP。全額返還のみでも精算作業としてA・Bの対象ですが、D・Eの3有効レースには数えません。
- Bは終了週で登録行が存在し全行確定した場合のみ。競馬をしなかった週はCのみ取得可能です。
- 週次振り返りは同一週1件。文章の訂正は可能ですが追加EXPなし。履歴の編集・削除で条件を満たさなくなればEXPと段階も再計算し、減点・退化の演出は行いません。
- カレンダー週を越えた精算や後日登録も開催日の週へ反映します。判定は端末の現在時刻を使用し、外部の証明とは扱いません。

## 安全な保存・復元

保存前に全体検証し、成功後だけIndexedDBを書き換えます。復元も同じ1トランザクションで全件置換するので、JSONパース・形式検証・トランザクション失敗時は既存データを保持します。30MBを超える復元ファイルは拒否します。未知のschemaVersionは拒否し、黙って変換しません。

将来の移行では、古いschemaVersionを新形式へ変換する関数を読み込み／復元処理の直前に追加し、成功後にのみ保存してください。DBの構造を変更する場合はdb.jsのVERSIONを上げてonupgradeneededで移行します。

ユーザーの文字列はHTMLエスケープして表示します。外部API・外部スクリプト・追跡通信はありません。公開サーバーへ送るのは静的ファイルの通常取得だけで、馬券情報は送信しません。

## テスト実行（開発者向け・利用者には不要）

計算テスト：`node --test tests/core.test.js`

ブラウザテスト：PlaywrightとChromiumを開発環境に用意して`node tests/browser.cjs`。テストが一時HTTPサーバーを立て、独立したブラウザプロファイルで実行します。ポート8000を使用。公開URLには実行しないでください。試験データはテスト専用プロファイルだけに保存します。

## 更新時

1. 実装変更と対応するテストを実施。
2. `sw.js`のVERSIONを必ず変更。必要ならpackage.json等の表示バージョンも変更。
3. 公開用16ファイルを再作成し、承認された公開先に配置。
4. アプリの「新しいバージョンがあります」から更新。未保存の入力中は更新を止めます。
5. Service Workerの更新はIndexedDBを削除しません。URLのホストを変えると別の保存領域になるのでJSONで移行してください。

本版は同一オリジンに1つのうまログを設置する想定です。同じホストの複数サブパスに設置するとIndexedDBは共有されます。今後の複数アプリ設置ではDB名を分けてください。
